# 2. Как работает RAG (высокоуровнево)

**RAG (Retrieval-Augmented Generation)** — сначала *ищем* подходящие реальные места в своей базе,
потом *генерируем* человеческое объяснение только про найденное. Проверка идентификаторов исключает вымышленные места из ответа; неточные формулировки ИИ всё ещё возможны.

## Схема

```
 Пользователь: «хочу кофе, у меня час» + точка + категории + язык ru/kk
        │
        ▼
 1. ДАННЫЕ       Отдельный запуск сборщика (кеш 24 ч): OpenStreetMap (Overpass) → база SQLite, 602 места Астаны
                 7 категорий: кафе, рестораны, парки, музеи, достопримечательности,
                 смотровые, детские площадки. Название, координаты, описание, часы, теги, источник.
        │
        ▼
 2. ПОИСК        Радиус ≈ (время − время на визит) × 75 м/мин ÷ 1,3.
   (Retrieval)   Фильтр по категориям → расстояние по прямой (Haversine) →
                 ранжирование: 0.5·категория + 0.3·совпадение слов + 0.2·близость →
                 до 12 кандидатов; если никто не укладывается — один близкий с budget_warning
        │
        ▼
 3. ГЕНЕРАЦИЯ    Gemini получает запрос, бюджет времени и ТОЛЬКО список кандидатов.
   (Generation)  Возвращает: id места, «почему подходит», «что сделать».
                 Точные координаты пользователя в модель не передаются.
        │
        ▼
 4. ПРОВЕРКА     id должен быть из списка кандидатов; повторы и выдуманные места отбрасываются;
                 фразы «открыто сейчас», «бесплатно», «есть Wi-Fi» без данных — отклоняются.
                 Название, координаты, часы, источник берутся из базы, не от модели.
        │
        ▼
 5. ОТВЕТ        1–3 места: расстояние по прямой, ≈ время, почему, что делать, часы (если есть),
                 источник. Если ИИ недоступен — те же реальные места с шаблонным объяснением.
        │
        ▼
 6. ИНТЕРФЕЙС    Карточки, карта, пометки источника пояснения, статуса по расписанию OSM и неизвестных данных.
```

## Что от поиска, а что от генерации

| Часть ответа | Откуда | Можно ли доверять |
|---|---|---|
| Название, координаты, категория, часы, источник | база (OSM) | исходные сведения могут устареть; источник указан |
| Расстояние, время на дорогу и визит | расчёт сервера | приблизительно, «по прямой» |
| «Почему подходит», «что сделать» | Gemini или шаблон | происхождение указано в `generated_by`; возможны неточности |
| Статус работы | расчёт backend по `opening_hours` OSM | только по расписанию, не фактическая проверка; неизвестное — `null` |
| Доступность для коляски | тег OSM `wheelchair` | только «по данным OSM», иначе «нет данных» |

## Как обрабатываем сомнительные и неполные данные

- **Нет или не удалось разобрать часы** — `is_open_now: null`, `status_note` сообщает, что часы не подтверждены.
- **Есть поддерживаемое расписание** — показываем открыто/закрыто **по расписанию OSM** и просьбу уточнить перед визитом. Закрытые по расписанию места не исключаются.
- **Нет описания** — ИИ опирается на категорию и не придумывает детали; шаблон честно пишет
  «соответствие остальным пожеланиям не подтверждено».
- **Нет данных о доступности** — «нет данных — уточните на месте».
- **ИИ не ответил или ответил некорректно** — те же реальные места, шаблонное объяснение (HTTP 200).
- **Ничего не нашлось** — пустой результат и совет изменить запрос; места «для заполнения» не создаём.
- **Временные события** (выставки, концерты) — в базе их нет, ИИ не может их обещать. `TODO` план развития.

## Пример живой проверки

18.10.2026: точка 51.09, 71.42; запрос «Жақын жерде қысқа серуендеуді қалаймын»;
60 минут, пешком, категории `park`, `attraction`, `viewpoint`, `language: "kk"`.

API вернул HTTP 200 за 6,6 с: «Тәуелсіздіктің 25 жылдығы», «Бейбітшілік пен Келісім аллеясы»
и «NU Park», с казахскими пояснениями и действиями. У всех `generated_by: "gemini"`, fallback не использовался.
Названия взяты из OSM; часы этих объектов неизвестны. Это один замер, а не гарантия времени ответа.
Полные вход и ответ: `live_check_language_kk` в [demo-results.json](../demo-results.json).
